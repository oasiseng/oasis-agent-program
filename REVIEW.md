# Maintainer acceptance checklist

Use this on each approved task. A receipt or passing CI cannot substitute for these decisions.

- [ ] Approved task identifies operator, public target/version, scope, criteria, reward/currency and payment arrangement.
- [ ] Target and contribution are public; no client/personal data or credentials leaked.
- [ ] Contribution is distinct from existing work; related findings are not split for extra rewards.
- [ ] Evidence reproduces the problem or supports the claimed opportunity.
- [ ] Deliverable meets the agreed criteria; no unrelated changes or hidden access requests.
- [ ] Sources, reuse rights and limitations are documented.
- [ ] Necessary tests were actually run; technical results are independently checkable.
- [ ] If AgentKit is required: open the receipt on the official verifier, check status/date/hash/URL, and separately confirm the operator's GitHub account. A screenshot is insufficient.
- [ ] Technical content is identified and assigned to a responsible PE; no unauthorized professional conclusions or seal/signature use.
- [ ] Record separately: bounty accepted, technical release approved, merged/published, and paid. These are different events.

## Owner decision record

Copy into the approved task, omitting private payout details:

```text
Task / target / reviewed commit or artifact hash:
Assigned operator:
Criteria checked and evidence:
Decision: accepted / revision requested / declined
Reason and any specific remaining revision:
Technical status: not technical / PE review pending / PE release recorded separately
Agreed reward and acceptance date:
Publication status:
Payment status: pending / recorded privately
Authorized Oasis reviewer:
```

Acceptance of a technical draft can satisfy its paid scope without authorizing construction, permitting or public reliance on its content. Record the PE release separately before publication where required.
